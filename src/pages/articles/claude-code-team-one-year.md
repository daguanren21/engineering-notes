> Claude Code 团队的工作方式并不是把同样的 Prompt 交给更强模型，而是持续提高自己操作系统的抽象层级：从监督每个 Tool Call，到交付一个目标，再到编排跨 Session 持续运行的 Loop 与 Routine。

meng shao 的文章整理了 Claude Code 团队三位工程师的一次圆桌对谈。参与者包括负责 Claude Code 的 Thariq Shihipar、负责 Workflows 的 Sid Bidasaria，以及负责 Claude Tag 的 Robert Boyce。他们回顾了加入团队约一年后，日常工作、产品设计和软件工程角色怎样改变。

这不是一份 API 功能清单。它讨论的是更难的部分：当模型能力每隔几个月发生明显变化时，团队如何决定哪些 Harness 继续保留、哪些功能应该删除，以及什么证据足以让工程师不再逐条监督 Agent。

文中的使用比例和效率数字来自原始访谈及整理文章，本文没有独立复核。更值得关注的是这些数字背后的系统机制。

## 变化的核心是抽象层级上移

一年前，工程师使用 Claude Code 的典型方式是：写 Prompt、盯着 Transcript、逐条反馈、逐个批准权限请求。

现在，他们描述的工作入口已经上移：

```text
监督 Token 和 Tool Call
        ↓
把一个完整目标交给 Agent
        ↓
让 Agent 在 Session 外持续运行
        ↓
用 Workflow 编排多个 Agent 和验证步骤
```

抽象层级每上移一次，人都减少一部分局部控制，同时要求系统提供更强的上下文、验证、权限和状态连续性。

这也是全文最重要的判断：模型能力提升只有转化成更高层的工作原语，才会真正改变生产方式。

## 从盯 Transcript 到交付目标

原文称，三位工程师现在有约 70–80% 的工作发生在 Claude Tag 中，只有约 20% 的精修或微观管理场景会回到 TUI 或桌面端。

比例本身不是普遍结论，但工作单位的变化很明确：

- 过去交付“实现这个类”或“写这个函数”；
- 现在交付一个需要研究、实现、协调和验证的端到端问题；
- 过去关注模型的每个决定；
- 现在主要关注目标、边界和最终证据。

这并不意味着中间过程不重要，而是中间过程不再要求人实时消费。Harness 应保存完整轨迹供审计，同时只把需要人判断的部分提升到界面。

## 上下文开始主动靠近 Agent

Claude Tag 运行在 Slack 中，能够检索产品讨论和团队历史决定。与把 Agent 单独放在终端相比，工作上下文本身就在它周围。

这是从“人搬运上下文”到“Agent 按需检索上下文”的变化：

```text
旧模式：人阅读 Slack → 摘要 → 粘贴到 Coding Agent
新模式：Agent 根据目标 → 检索 Slack 与项目历史 → 带来源执行
```

减少人工搬运不等于允许无限读取。好的 Harness 仍需明确：哪些频道可访问、哪些内容可以进入代码任务、来源如何记录、敏感信息能否离开原边界。

上下文越靠近 Agent，权限与数据分类就越需要成为基础设施。

## 为“两个月一换代”的技术造产品

访谈把 AI 产品的特殊难题概括为：底层模型能力大约每两个月就会在产品脚下发生一次明显位移，而且周期还在缩短。

团队必须同时完成两件互相拉扯的事：

1. 为今天的用户解决真实失败；
2. 不把今天的模型缺陷固化成长期产品结构。

许多 Harness 功能本质上是能力补丁。模型不会规划，就增加 Todo；不会正确询问，就设计 Ask Tool；无法长程连续，就增加外部记忆。补丁在当下可能非常有效，但模型行为改变后，它也可能成为多余协议和交互负担。

所以 Agent 产品不能只问“还缺什么功能”，还要持续问“哪些功能已经不再需要”。

## 舍得删除自己造的 Harness

原文举了两个例子。

Todo List 在早期 Sonnet 3.5 时代帮助模型记住长任务中的多个步骤。当模型只能完成五项中的三项时，它是有效的外部约束。一年后，随着模型规划和记忆方式变化，旧 Todo 形态的重要性下降，团队转向更复杂的连续性机制。

AskUserQuestion Tool 也经历了类似周期：早期需要大量设计才能让模型正确调用；模型后来学会使用；再后来，工程师在一些场景中直接让 Claude 生成包含图表和 Mockup 的 HTML Artifact，以更具体的方式呈现问题。

真正困难的不是造出功能，而是承认功能完成了历史使命。

删除标准应该来自 Eval：移除后，任务完成率、错误率和人工介入没有变差，这个功能就是成本；如果关键指标下降，再恢复并重新定义它的职责。

## 用可组合原语抵抗产品过时

团队的方法不是预测两年后的完整产品，而是构建可叠加的原语：

- 权限；
- 可视化 Artifact；
- 记忆；
- 验证；
- 反馈；
- Review；
- Agent 调度。

固定 Workflow 很容易被下一代模型绕开或淘汰；稳定原语可以重新组合成新的工作方式。

例如“截图”不应只属于某个前端流程。它是可复用的验证证据，可以进入 Coding Review、视觉回归、Bug 报告和跨 Agent 交接。

一个原语值得保留，通常因为它拥有清楚语义、可观察状态和稳定边界，而不是因为某个页面正在使用它。

## Loops 和 Routines 如何出现

访谈描述了一条非常务实的演进路线：

1. Agent 在本地笔记本运行，关机后任务停止；
2. 改用远程开发机，但需要 SSH 回去管理；
3. 发展出 Web 端托管容器，让任务持续后台运行；
4. 有了持续环境后，再加入按计划触发的 Routine。

云端并不是起点，而是“任务需要突破单个 Session 和本地机器生命周期”之后产生的基础设施答案。

原文举例：系统可以每天汇总反馈、按重要性分类，并自动修复高置信度问题。这里的关键不只是定时器，而是 Routine 同时需要：

```text
触发条件 + 可恢复状态 + 权限 + 验证 + 停止条件 + 人工升级
```

没有这些约束，持续运行只会让错误持续更久。

## 代码审查正在重新分工

传统 Review 中有大量局部工作：格式、小 Bug、漏测分支和常规一致性问题。模型已经能并行检查并自动修复其中很多部分。

人的价值因此上移到模型难以从 Diff 单独恢复的背景：

- 为什么 API 要这样设计；
- 服务边界为什么画在这里；
- 哪个短期捷径会破坏长期产品方向；
- 哪些风险值得承担；
- 哪些事实来自组织历史而不是代码。

理想分工不是 Agent 写、人逐行重做，而是 Agent 把局部问题清理并组织相关证据，人审查架构意图和系统后果。

如果 Reviewer 仍需从头查找所有上下文，自动生成代码并没有降低 Review 成本，只是把成本移动到了队尾。

## Fan-out 之后必须 Reduce

代码审查是团队较早大规模使用 Fan-out 的场景：多个 Agent 并行搜索潜在 Bug，再从不同视角对候选问题进行对抗式检查，最后只把高置信度结果交给人。

这是一种 MapReduce 形状：

```text
MAP
并行查找安全、性能、正确性与边界问题
        ↓
VERIFY
多个视角判断候选是否真实
        ↓
REDUCE
去重、排序、保留证据充分的问题
```

Fan-out 会快速放大信息量。如果没有 Reduce，人类收到的是十份重复报告和大量误报，注意力成本反而上升。

Test-time Compute 的价值不在“多跑几个 Agent”，而在把额外算力投入到候选验证和信息压缩，得到更可信、可消费的结果。

## 确定性代码和 Agentic 行为混合

Workflows 的关键洞察是让 Agent 自己构造 Harness：决定如何 Fan-out、怎样把一层输出交给下一层、最后如何汇总。

但整个过程并非完全交给自然语言。更可靠的形式是：

```text
确定性代码控制拓扑、遍历、预算和完成条件
LLM 处理分类、推理、生成和局部修复
```

`for` 循环不会忘记数组里的第三项；类型和状态机会保证所有分支都经过同一处理。模型则负责那些无法提前写成确定性规则的判断。

信任来自这两层的组合。纯代码不够灵活，纯 Agent 行为又可能漏项；用代码固定结构，用模型填充判断，系统更容易解释和恢复。

## UI 第一次与 Transcript 解耦

Claude Tag 中，Slack 用户看到的消息不是完整 Transcript 的逐行直播，而是 Agent 主动调用“发送消息”工具产生的沟通。

这让两个概念第一次彻底分开：

- Transcript 是审计与恢复协议；
- UI 是 Agent 选择与人沟通的内容。

早期看不到模型的每一步会让工程师不安，但如果结果、验证和完整日志都可访问，持续观看思考过程并不是建立信任的唯一方式。

界面应该优先展示目标、状态、风险、需要决策的问题和验证结果。把所有内部过程直接倾倒给用户，只是让人重新成为运行时监控器。

## 信任来自验证与反馈闭环

访谈中的实践案例串起三类原语：

1. Verification：Agent 自测、截图、录屏和运行真实界面；
2. Code Review：独立检查并过滤低价值问题；
3. Feedback：连接指标、事件、Slack 讨论和 GitHub Issue。

信任不是因为模型“看起来更聪明”，而是系统不断产生可检查证据。

一个 Agent 可以提出产品改进、生成 Mockup、实现功能并监控使用情况，但每个阶段都要有自己的证据和退出条件。反馈下降时，下一步应该重新提出方案，而不是机械继续最初的人类想法。

这使人与 Agent 的关系从“执行我的具体方案”变成“围绕同一目标共同寻找更好的方案”。

## 人的价值移向架构意图

访谈中，工程师提到过去享受手写性能优化或复杂 CSS，如今模型在一些局部实现上已经更快、更好。失去亲手处理细节的满足感是真实变化。

与此同时，人的工作并没有消失，而是转向：

- 产生值得解决的新问题；
- 决定系统边界；
- 判断架构意图；
- 推动需要多方认同的改变；
- 缩短想法、原型和生产之间的距离。

这种上移有代价：工程师可能在单一实现领域少一些亲手积累，也更依赖验证系统判断 Agent 是否真的做对。组织需要主动保留理解底层的能力，不能把“更少手写”误解为“不再需要技术判断”。

## 五个可以带走的判断

从整场对谈可以提炼出五条可迁移原则：

1. **抽象层级持续上移。** 工作单位会从 Tool Call 变成目标，再变成跨 Session 的 Loop；每次上移都需要更强状态与验证。
2. **Harness 应该可以被删除。** 它为当前模型缺陷服务，Eval 证明不再需要时就移除。
3. **信任需要两个来源。** 验证提供事实，确定性编排保证覆盖和顺序。
4. **人的判断移向系统层。** 局部 Nit 可以自动化，架构意图、边界和后果仍需要明确 Owner。
5. **Fan-out 必须配套 Reduce。** 增加 Agent 只会增加输出；候选验证、去重和压缩才会减少人的注意力成本。

这些原则并不要求采用 Claude Tag 或特定产品。它们适用于任何准备让 Agent 从“可交互工具”升级为“持续工作系统”的团队。
