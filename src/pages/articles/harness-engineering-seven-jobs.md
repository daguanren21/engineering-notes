> 当 Agent 反复失败时，先别急着换提示词、模型或上下文窗口。先检查模型周围的工作系统是否给了它明确目标、正确工具、持久状态和可验证的完成条件。

rari 的文章从一个常见误区开始：Agent 忘记决定、用错工具、跳过验证或卡在循环里，人们通常先修改 Prompt，再换模型，最后加大 Context Window。问题依旧存在，因为真正失效的可能不是推理能力，而是承载推理的环境。

这篇阅读笔记把原文的产品化表达压缩成一套工程检查表。核心不是“给模型更多自由”，而是明确哪些事情由模型判断，哪些事情必须由 Harness 强制。

## 先判断问题属于模型还是环境

Agent 的失败至少有两种来源：

1. **能力不足**：模型确实不会推理、无法理解问题或缺少必要知识；
2. **环境不足**：目标模糊、上下文缺失、工具反馈含糊、状态会丢失，或者系统没有验证出口。

两者的修复完全不同。能力问题可能需要更好的模型；环境问题即使换模型，也只是让同一种失败变得更贵。

可以先问四个问题：

- 执行前是否已经写清楚成功条件？
- Agent 是否能找到必要知识，而不是加载整座仓库？
- 工具失败时，模型能否知道失败发生在哪里？
- 模型说“完成”时，系统是否有独立证据？

如果答案是否定的，继续调 Prompt 往往只是在绕开结构缺陷。

## 模型只是推理引擎

模型能提出下一步，但它无法凭自身创造可靠的运行环境。Harness 决定：

```text
模型能看到什么
模型可以触碰什么
哪些状态能跨会话存活
什么算作完成证据
何时允许重试
何时必须停止或升级给人
```

因此 Prompt 只是系统中的一个组件，模型也只是一个组件。最终产品是上下文、工具、状态、权限、验证和恢复共同工作的结果。

可以用一句话区分两类工程：

> Prompt Engineering 改善指令；Harness Engineering 改善指令被执行的条件。

## 同一个模型为什么会变成不同的 Agent

同一个模型放进聊天框，只会回答问题；放进一个拥有仓库、终端、测试、浏览器、项目记忆、隔离工作区和 Review Loop 的环境，它才可能交付软件。

权重没有变化，变化的是可执行能力与反馈回路。

这也解释了为什么不同 Coding Agent 即使使用相同底模，表现仍可能差异巨大。比较它们时，不能只看模型名，还要看：

| 层 | 应检查什么 |
| --- | --- |
| 上下文 | 是否能按需找到项目知识 |
| 工具 | 输入输出是否稳定、失败是否明确 |
| 环境 | 是否隔离、可复现、可初始化 |
| 状态 | 决定与进度是否在对话外持久化 |
| 反馈 | 是否有独立验证和修复路径 |
| 控制 | 是否有预算、权限与停止条件 |

原文把生产级 Harness 的职责分成七项。

## 一、把请求变成契约

执行前，把自然语言请求转换成有边界的任务对象：

```json
{
  "goal": "交付功能",
  "inputs": ["Issue", "仓库", "设计约束"],
  "output": "可审查的变更",
  "constraints": ["不修改数据库 Schema", "保持公开 API"],
  "doneWhen": ["类型检查通过", "真实界面验证通过", "Review 通过"]
}
```

契约的作用不是增加文档，而是防止任务被静默改写。没有契约，Agent 很可能完成一个更容易的问题，然后把它称为成功。

好的任务契约至少写清楚：对象、范围、允许的副作用、不可改变的约束、交付物和可观察验收标准。

## 二、给 Agent 一张地图

Agent 需要项目知识，但不需要每次把所有文档塞进上下文。

根目录指南应该像目录页：说明架构入口、测试入口、产品规则、安全边界，以及遇到某类任务时应该继续读哪里。详细规则放在它真正控制的代码或工作流附近，需要时再加载。

```text
AGENTS.md
├── 架构地图
├── 测试地图
├── 产品规则入口
├── 安全规则入口
└── 任务专用指南入口
```

小地图节省上下文；巨型手册消耗上下文。判断标准不是文件有多全，而是 Agent 能否用最少读取抵达正确事实。

## 三、在正确环境暴露正确工具

工具不是一排按钮，而是模型与现实世界之间的接口。每个工具都需要：

- 单一且明确的语义；
- 可预测的结构化输出；
- 明确的错误状态；
- 与副作用匹配的权限边界；
- 输出、时间和资源上限。

权限应按能力划分，而不是按工具名字划分：工作区内读取可以默认允许，沙箱内测试可以允许；网络、部署、删除数据和触达他人则需要更严格的策略或人工批准。

好的工具会在模型开始错误推理之前先消除歧义；坏工具迫使模型猜测“刚才到底发生了什么”。

## 四、把记忆外置为持久状态

对话不是 System of Record。任务决定、生成物、失败、风险和待办必须存在 Context Window 之外。

```json
{
  "taskId": "task_042",
  "currentStep": "verify_ui",
  "artifacts": ["build", "report", "screenshot"],
  "decisions": ["保持现有 Schema"],
  "failures": ["390px 下存在横向溢出"],
  "pending": ["等待人工批准"]
}
```

下一次会话应该继承工作状态，而不是依赖一份有损的聊天摘要。这是 Agent 穿过压缩、崩溃、切换模型和人工交接后仍能继续工作的基础。

## 五、先加传感器，再加自治

Agent 无法修复自己看不到的问题。测试、类型检查、截图、日志、指标和 Schema Validator 都是 Harness 的传感器。

不同产物需要不同证据：

| 产物 | 最小证据 |
| --- | --- |
| 代码 | 运行、类型检查、相关测试 |
| UI | 真实页面、交互、截图与可访问状态 |
| 研究 | 来源、矛盾检查、不确定性标注 |
| 数据 | Schema、范围、新鲜度检查 |

模型创建产物，环境生成证据，Harness 决定证据是否足以继续。没有这一步，“自我反思”很容易退化成模型再次同意自己的第一次判断。

## 六、在模型之外执行权限策略

模型可以建议动作，但不应该同时承担计划、批准风险和执行副作用三个角色。

```text
MODEL SUGGESTS → POLICY CHECKS → TOOL EXECUTES
```

动作越昂贵、越不可逆、越会影响他人，这个分离越重要。部署、付款、删除远端资源、修改生产数据和发送外部消息，都应该由模型外部的确定性策略或人工门禁授权。

这不是不信任某个模型，而是不把概率系统当作自己的权限管理员。

## 七、记录轨迹并局部恢复

每次运行都应留下可读轨迹：

- 原始请求与选中的上下文；
- 工具调用和状态变化；
- 验证结果与重试；
- 成本、最终产物和回滚点。

没有轨迹，失败是一桩谜案；有轨迹，失败会变成下一次改进 Harness 的输入。完整轨迹也使模型升级可以比较、回归可以归因、审计可以执行，而不是被最终回答掩盖。

## 让规则从说明升级为基础设施

重要规则应该至少表达两次：

1. 用说明告诉 Agent 为什么；
2. 用机械检查保证它不能绕过。

例如，“UI 层不能直接访问数据库”可以写进架构指南，同时由 Lint Rule 禁止 UI 导入 Repository Layer。

指南负责解释，检查负责执行。一旦这样做，下一次 Agent 不必记住过去发生过什么，系统已经替它记住了失败。

## 循环属于 Harness

“不断尝试直到成功”不是控制系统。可用的循环必须拥有证据、有界重试、预算和升级路径：

```ts
for (let attempt = 1; attempt <= 3; attempt += 1) {
  const artifact = await build(state)
  const evidence = await verify(artifact)

  if (evidence.pass) return artifact

  state.failures.push(evidence.gap)
  state.repair = evidence.repair
}

return requestHumanReview(state)
```

模型可以决定如何修复局部缺口；Harness 决定是否还允许下一次尝试。

## 失败应该升级系统

普通修复只处理当前输出，Harness 修复处理一类失败：

| 失败 | 应升级的系统能力 |
| --- | --- |
| 缺少上下文 | 增加地图或检索规则 |
| 用错工具 | 改善工具语义或路由 |
| 输出格式错误 | 增加 Validator 或契约 |
| 反复循环 | 增加重试上限和升级路径 |
| 危险动作 | 增加权限门禁 |
| 决定丢失 | 写入持久状态 |
| 原因未知 | 增加 Trace 与证据采集 |

一次 Patch 只修一轮；一次 Harness 改进会影响此后的每一轮。这就是复利所在。

## 分开大脑、双手与历史

可靠 Agent 更容易被拆成三个部分：

```text
BRAIN   模型，负责推理
HANDS   沙箱与工具，负责行动
HISTORY 追加式记录，负责保存发生过的事实
```

沙箱崩溃，历史仍然存在；模型更换，工具和策略仍然可检查；任务恢复，新会话可以通过状态和产物重建现场。

这个分离也是安全与可恢复性的共同边界：执行单元可以被杀死，但不应该带走会话权威。

## 从能闭环的最小 Harness 开始

Harness Engineering 不意味着先造平台。原文给出了一条逐级增加复杂度的路线：

```text
LEVEL 0  Prompt + Model
LEVEL 1  Project Guide + Tools
LEVEL 2  Structured State + Tests + Bounded Loop
LEVEL 3  Permissions + Traces + Recovery + Human Gates
```

低风险短任务可能只需要 Prompt 和一次 Review；可以修改文件、访问网络并运行数小时的任务，需要真正的 Harness。

最稳妥的判断是：**Harness 应小于它所控制的失败面，但必须完整覆盖那个失败面。**先完成最小闭环，再让真实失败决定下一层基础设施，而不是预先把所有复杂系统搬进来。
