> Harness 的价值不是让一次模型调用跑起来，而是让状态、执行和交互在长时间、并发、失败与不可信输入下仍然可信。

《The Harness Playbook》不是一篇教你写 Agent Loop 的入门教程。它更像是 omp 的事故复盘，以及 omp² 的架构说明书。作者用一个贯穿全文的判断组织了状态、运行时、配置、模型兼容、工具和界面这些看似分散的问题：**不可避免的复杂度必须有明确的主人。**

如果框架为了“简单”而不处理复杂度，复杂度并不会消失。它只会流向插件、脚本和用户，让每个调用者实现一份只有三成功能的版本。

## 一句话结论

Agent Harness 是系统软件，不是套在 `fetch()` 外面的循环。

它同时承担了类似游戏引擎的职责：维护权威世界、记录状态变化、调度参与者、执行不可信操作、同步多个视图、适配不同协议，并实时渲染界面。评价它时，不能只看“调用模型的代码有多短”，而要看它是否能在恢复、并发、取消、远程访问和恶意输入下维持同一套事实。

文章给出了五条总约束：

1. 整个会话只能有一个权威状态；
2. 策略留在可信宿主，沙箱只执行有限请求；
3. 工具、子 Agent 和后台任务都必须有边界、可取消、可观察；
4. 模型与 Provider 的差异必须成为结构化知识；
5. TUI、Web、远程客户端只是同一状态的不同投影。

后面的设计基本都是这五条约束的推论。

## 先用四种极端场景审问架构

作者没有先讨论类、接口或数据库，而是先要求 Harness 同时扛住四种运行方式：

| 场景 | 关键压力 |
| --- | --- |
| 多 Agent 本地工作区 | 多个参与者共享目录并发工作 |
| 远程控制 | 手机或远端客户端控制另一台机器上的 Agent |
| 旁观者模式 | 多个客户端只读观看会话 |
| 自动化软件工厂 | 无人值守地处理不可信仓库和工具输出 |

只为“本地单用户聊天”设计的框架，很容易把控制器塞进 TUI，把状态放进闭包，让插件与引擎共用进程，并默认人类能随时救场。四种模式一起考虑，会迫使系统提前划清状态、信任与执行边界。

这是一种值得复用的架构方法：**不要先问最常见场景能不能跑，要先找出会让边界崩溃的场景。**

## 状态：恢复聊天记录不等于恢复会话

Pi 风格的 Harness 通常把消息树写入 JSONL，但真正影响行为的状态还散落在其他地方：

- Todo 和工作流状态；
- Plan、Goal 等模式开关；
- 动态工具注册表；
- 子 Agent 列表；
- 重试次数和流式标记；
- 插件闭包里的 `Map`、`Set` 和计数器。

这会制造两个权威来源。聊天记录可以回退，但内存状态可能停留在未来；程序可以恢复，但动态工具和计数器可能回到默认值；分支已经废弃，其中的保存记录却可能重新出现。

作者检查了 Pi 的官方有状态扩展示例：17 个里只有 2 个正确处理了状态恢复。这个比例说明，问题不该继续归咎于扩展作者“不够谨慎”。如果正确性依赖每个插件都记住多个恢复钩子，API 本身就在把错误设计成默认路径。

omp² 的答案是把完整会话物化为一棵状态树：

```xml
<meta>
  <todo>...</todo>
  <jobs>...</jobs>
</meta>
<body>
  <user id="e12">...</user>
  <ai id="e13">...</ai>
  <Read id="e14" status="ok">
    <input path="src/main.rs:1-80" />
    <result lines="80">...</result>
  </Read>
</body>
<queues>
  <steering>...</steering>
</queues>
```

日志记录这棵树的属性变化。运行时可以建立缓存和索引，但不能成为第二份真相。

于是几个难题变成同一件事：

- **恢复**：重放日志，重新物化整棵树；
- **回退**：比较当前状态和目标状态的差异；
- **分支**：从任意日志位置复制完整会话；
- **同步**：远程客户端订阅状态补丁；
- **渲染**：不同客户端读取同一状态，生成自己的界面。

最重要的收益不是 XML，而是这条约束：添加一个有状态功能，不应该再给 rewind、fork、resume 和 replication 分别增加处理逻辑。

## 运行时：宿主决定，沙箱执行

把所有东西都扔进 VM 看起来最安全，实际会迅速陷入矛盾：要么 VM 无法调用宿主工具，要么必须开放一条双向通道；会话存储放在外部，又要给 VM 写权限；整个应用放进 VM，还会泄露内部提示词和源代码。

文章给出的边界更克制：

**可信宿主负责：**

- 会话状态与日志；
- 模型推理；
- 权限、审批和限额；
- 工具路由与任务调度。

**沙箱负责：**

- 执行一个明确、有限的环境操作；
- 通过有大小上限的流返回结果。

同一原则也适用于子 Agent。Worktree 只能隔离 Git 追踪的文件，不能覆盖整个工作区。更完整的做法是给子 Agent 一个写时复制的文件系统视图：子 Agent 在自己的视图里修改，父 Agent 最后只接收差异，而不是与它共享可变权威。

## 工具调用应该是一条状态流

传统工具 API 常被拆成三个互不相干的回调：

```ts
renderCall(args)
execute(params)
renderResult(result)
```

以 Edit 为例，预览可能先读文件并计算 diff，执行阶段再读一次、再算一次，结果渲染又要解析执行返回的字符串。流式输出、诊断、取消和日志记录还需要额外协议。

问题不是代码重复，而是系统没有一个代表“这一次调用”的权威对象。

omp² 把调用建模为不断变化的结构化状态：

```xml
<Edit id="e41" status="running" version="3">
  <input i="修改解析器，不改变公开 API">...</input>
  <result>...持续更新的结构化结果...</result>
  <diag severity="warn">...</diag>
  <usage elapsed-ms="842" />
</Edit>
```

执行器只更新这个对象。模型、用户、日志、远程客户端和测试框架读取不同投影，不再从一段展示文本中反向恢复结构。

由此还得到两个重要结论：

1. 输出大小和前台阻塞时间必须由统一原语限制，不能靠每个工具主动调用截断函数；
2. 取消必须有可被强制终止的执行边界，`AbortSignal` 和 `context.Context` 只能表达协作意愿，不能杀死忽略信号的代码。

## Job：把所有长时间工作合并成一种概念

后台 Shell、子 Agent、开发服务器、远程函数，以及超过前台预算的普通工具，本质上都有相同形状：

```text
stdin + stdout + exit status + signal handle
```

所以它们应该统一为 Job，由一个地方负责：

- 前台阻塞预算；
- 转入后台；
- 输出溢出到 Artifact；
- 查看、发消息和终止；
- 并发上限和状态观测。

这比为 Bash、Task、服务器和远程调用分别增加一套 `spawn/list/poll/kill` 更容易保持一致。它也允许多个 Agent 发现并复用同一个工作区服务，而不是各自启动一份开发服务器。

## 控制平面：值用 ConVar，行为用 Director

控制平面处理两类问题：

- **值**：当前模型、服务等级、主题和策略是什么；
- **行为**：Agent 是否可以结束、是否必须继续一轮、是否临时需要某项能力。

### 值：在定义处声明生命周期

文章借鉴 Source Engine 的 ConVar。一个设置在定义时就声明类型、默认值、帮助文本，以及作用域、持久化、同步、权限等属性。

会话级配置仍然是权威状态树中的节点，而不是旁边的第二个设置数据库。创建子 Agent 时默认复制父级当前值；需要覆盖时加载对应 profile。这样不必为每个设置再发明一个 `subagentXxx` 字段。

配置文件、命令行、快捷键、远程管理和日志重放也可以共享同一种命令语言，避免每个入口维护一套 Schema。

### 行为：Director 栈统一拥有“能否结束”

Plan、Goal、强制工具调用和 Todo 提醒都有一个共同需求：它们需要拦截模型准备结束的时刻，并决定是否继续。

如果每个插件自己维护模式开关和互斥锁，不同作者的工作流就无法可靠组合。文章提出由 Agent 层维护一个 Director 栈：

```text
Base → TodoReminder → Goal → Plan → ForceTool(write)
```

推理前从外向内修改请求；模型准备结束时从内向外处理候选 Yield。每个 Director 可以放行、继续、结束、压入子 Director、完成弹出或失败。

例如 Plan 发现计划文件还没写，可以临时压入 `ForceTool(write)`。写完后子 Director 弹出，同一个候选 Yield 再交回 Plan 判断。Plan、Goal 和扩展工作流因此使用同一套组合规则，不必知道彼此的私有实现。

## 推理层：兼容性是知识库，不是 if-else 集合

模型能力取决于模型家族、版本、宿主、API、代理和推理模式。继续堆积：

```ts
if (isKimi) { ... }
else if (isClaudeOnBedrock) { ... }
else if (isDeepSeekBehindProxy) { ... }
```

会让同一事实散落在请求构造、模型发现、Thinking、Tool Calling 和序列化代码中。

文章把知识拆成三层：

```text
taxonomy/   这个模型字符串代表什么
classes/    这个模型家族具有什么性质
providers/  托管平台改变了什么
```

关键不是换成 KDL，而是让编译器强制规则具备明确优先级：未知指令报错，相同精度的冲突规则报错，没有证据时返回 `unknown`，而不是偷偷当作 `false`。

一个完整的推理适配层还应该集中处理：

- 畸形 JSON 修复；
- 重复循环检测；
- 模型特有的 Tool Call 和 Thinking 方言；
- Provider 的认证刷新、重试和 Token 统计；
- Strict Schema 的共享额度；
- 强制工具调用的提示、原生参数和有界升级策略。

“能打开流”只是连通性，不代表其他 Harness 已经收到一轮规范、可信的结果。

## 工具面：少而深，而不是多而浅

每个永久工具 Schema 都会占用请求前缀，并影响模型生成合法参数的过程。文章报告，在特定基准中把工具收缩到五个后，omp 的墙钟时间从明显落后变为快于对照实现。

频繁动态增删工具也不理想，因为会让 Provider 缓存失效。更好的方向是保持一个很小、稳定的永久语法，把长尾能力放到稳定入口后面：

```sh
dyn github/list_prs --state open
dyn database/query @query.sql
dyn image_gen "blueprint of a frog"
```

对于浏览器这类开放操作集合，则暴露持久代码接口，让多个动作在一次调用中组合。

可以把选择原则压缩成一句话：

> 有限操作集合用 Schema；开放操作集合用命令或代码表面。

小工具表面要求内置原语足够“深”。`Read` 不只是读取文本文件，而是“把资源物化为最适合推理的表示”：目录、网页、PDF、数据库、图片、压缩包、Notebook、远程文件和内部 URL 都可以共享这个意图。

这不是为了做万能函数，而是把资源差异放进唯一拥有它的层。**Read 本身复杂，读取这件事才会简单。**

## 界面：字符串不能同时充当内容、布局和终端程序

当组件返回带 ANSI 的 `string[]` 时，这些字符串同时承担内容、样式、布局、传输和终端控制。后果包括：

- 每帧重复拼接、切割、测量和解析；
- Unicode 宽度、截断和 Resize 错误；
- 插件自行决定颜色、图标和边框；
- 未清洗的外部文本可以注入 ANSI 控制序列；
- 已进入原生 Scrollback 的内容无法可靠改写。

omp² 的方向分两层：底层让 RichText 通过单次流式管线进入帧差异；上层使用类型化组件描述结构和语义。插件表达的是 `info`、`error`、`<badge>` 或 `<pre>`，具体颜色、图标、换行和截断由渲染器统一决定。

文章还把终端 Transcript 当作正式协议，区分：

- 可被整体替换的临时块；
- 只能追加的流式块；
- 已完成但尚未进入历史的块；
- 已经不可逆地进入 Scrollback 的内容。

因为 Resize、流式输出和原生 Scrollback 的组合很难凭直觉保证正确，作者用 TLA+ 描述不变量并寻找反例。这里最值得带走的不是特定状态机，而是方法：**对真正难以测试的并发与生命周期问题，先给出可验证的协议，再写渲染代码。**

## 技术栈是约束的一部分

作者最终选择 Rust 作为核心、Python 作为扩展语言，并明确反对在没有前端互操作需求时默认使用 TypeScript。

这个判断很有个人立场，但论据值得重视：在大量代码由 Agent 生成的环境里，语言的默认项目结构、标准库、编译器反馈和生态惯例会成为生成结果的先验。允许二十种同样常见写法的语言，会让模型在解决产品问题之前先做二十个风格决定。

具体语言不必照搬。可迁移的原则是：**技术选型不只决定运行性能，也决定未来贡献者和 Coding Agent 最容易写出什么样的代码。**

## 哪些是原则，哪些只是实现选择

文章很容易让人记住 DOM、XML、ConVar、Director、Rust 和 Python，但这些名词不是结论本身。

| 可迁移原则 | omp² 的具体选择 |
| --- | --- |
| 一个可重放的权威状态 | DOM/XML 与属性补丁日志 |
| 策略和执行分离 | Host + Sandbox Stub |
| 长任务统一生命周期 | stdio 形状的 Job |
| 多轮行为可组合 | Director 栈 |
| 兼容规则集中且有优先级 | 编译后的 KDL 规则 |
| UI 描述语义而非终端字符串 | 类型化组件与 RichText 管线 |
| 困难不变量先形式化 | TLA+ Transcript 模型 |
| 语言约束应帮助维护架构 | Rust 核心 + Python 扩展 |

因此，读这篇文章时最不该做的是照着复制类名；最应该做的是找到自己系统中的第二份真相、可无限阻塞的调用、散落的 Provider 判断，以及要求每个插件重复实现的安全边界。

## 最后判断

这篇文章最有价值的不是证明 omp² 已经解决了所有问题。作者明确说明其中一些设计已经实现，一些仍在建设或推演。它真正提供的是一套判断 Harness 是否可靠的检查方式：

1. 任意时刻的完整会话能否只通过日志恢复？
2. 不可信执行能否耗尽宿主资源或带走会话权威？
3. 任意工具是否都有统一的截断、超时、后台化和强制终止？
4. 两个独立工作流能否组合，而不是互相识别私有开关？
5. Provider 差异是否有唯一、可检查的知识来源？
6. 新能力是否一定要永久增加模型工具语法？
7. 多个界面是否渲染同一事实？
8. 最困难的生命周期是否有明确不变量和可执行验证方式？

如果其中多数答案是否定的，系统现在的“简单”很可能只是把成本延期，并转嫁给了每一个调用者。
