## 把重复流程交给平台，而不是交给采购

事件运营的痛点不在决策，而在决策之后那段固定序列：复制落地页、生成一组 UTM 链接、起草邀请邮件、加进两个项目看板、每天早上导出注册名单清洗后同步、活动结束后导出参会者、改列名、打标签、写报告。每一步都不难，难的是每一步都可能贴错链接、漏掉一天、拼错一个下游 15 份报告都依赖的 campaign 名。

作者的做法不是买一套营销自动化平台，而是把已有的 GitHub 原语当成执行引擎。理由很直接：APAC 不是一个市场，同一场 webinar 这个月在东京用日文跑、下个月在首尔用韩文跑，分群不同、CRM 字段不同、对「好线索」的定义也不同。让打包工具吸收这些差异意味着定制预算、咨询工时和等别人的 roadmap；自己搭则意味着流程变更就是一个 pull request。

前提条件只有一个：你重复劳动经过的工具要有可脚本化的入口——API 或者 CLI 都行。事件平台提供 API，CRM 连 API key 都不用配，官方 CLI 走浏览器登录就完成了认证。

## Issue 是工作单元，标签是开关

系统建立在三个原语上，各自职责清晰：

- **Issue 表单是申请表。** 不是空白文本框，而是结构化字段：事件标题、日期、区域、campaign 名、目标受众。每种事件类型（webinar、线下活动）一张表单，喂给同一套机器。
- **标签是开关。** `event-setup` 不是分类标签，是触发器。每个工作流的第一个条件就是「只有这个标签存在时才跑」。
- **Actions 是机器。** 标签落下时触发，从 Issue 正文里解析表单字段，然后去干活。

仓库给开发者的一切，这里免费给了营销流程：历史、可见性、评审，以及每个决定都有一个 URL。

`event-setup` 标签落下的几分钟内，工作流完成过去要花大半天的事：在事件平台复制旧活动生成新落地页、生成全套格式一致的 UTM 链接、把邀请邮件生成为 Word 文档并提交进仓库、向发信团队和区域营销团队开请求 Issue、把活动加进项目看板并填好字段、最后在 Issue 上回帖汇总，让下一个打开的人一眼看到全部状态。

注册筛选走的是定时而非标签：每天早上 cron 触发的工作流拉取所有进行中活动的最新注册者，清洗后共享名单。邀请制活动还会按标准筛 waitlist——这个注册者是目标企业账号的开发者、学生，还是非常想来听高管闭门会的竞品。

## 对话放在流水线最前面，是为了留出例外

流水线在 Issue 存在之前就开始了。作者打开 Copilot 说一句「我想在 11 月办一场关于 AI 辅助开发的 webinar」，接下来发生什么由仓库根目录的 `AGENTS.md` 决定。这份纯 Markdown 的团队 runbook 定义了 campaign 怎么命名、财季怎么映射到日期、每个区域用哪个时区、一封好的邀请邮件长什么样。Copilot 读完它，找到相似的历史活动，按命名规则提出 campaign 名，起草两版邀请邮件，并问出 runbook 规定要问的问题。

把对话放在最前面是刻意的设计取舍。全自动化就失去灵活性——某一场活动想稍微不一样时，刚性流水线没有地方表达；全人工填则必然出错。对话正好卡在中间：Copilot 遵循模板，所以落进 Issue 的数据格式正确；因为它是对话，所以可以为这一场活动弯折细节而不破坏下游机器。

分工必须说清楚：**Copilot 起草，人做决定。** 每个 campaign 名、每个邮件主题、每个日期都要签字确认，之后机器才接管。早期这段对话发生在 Copilot CLI 的终端里，对作者没问题，但「打开终端」对很多人是门槛；换成 Copilot 桌面应用后，门槛从「熟悉 shell」降到「会打字」。

## DRY_RUN 是敢做实验的原因

作者最满意的设计是一个叫 `DRY_RUN` 的开关，存在仓库变量里，每个工作流运行前都检查它。打开后所有工作流照常走一遍流程，但不碰任何外部系统：不建落地页、不在其他仓库开 Issue、不共享名单。一个自己给自己做自动化的营销团队需要排练的余地，`DRY_RUN` 就是排练开关。

活动收尾过去是最难受的部分，现在只剩两条命令：`/lead-upload` 拉取参会名单、整形成营销运营团队做 CRM 上传所需的精确格式、开请求 Issue 并关闭跟踪 Issue；`/event-report` 拉取出席指标和问卷结果，把报告作为评论发在活动 Issue 上——回到那个装着这场活动一切的 URL。

这两条是 Copilot agent skills，而 skill 就是一个 Markdown 文件。每个 skill 是一份 `SKILL.md`：用散文写成的程序，告诉 Copilot 做什么、按什么顺序、注意什么。作者说它们读起来就像她以前记在脑子里的 runbook，因为它们本来就是。**能写 runbook，就能写 skill。**

skill 也是系统保持灵活的原因。APAC 没有两个市场的收尾方式完全相同，硬编码的工作流会把所有市场压成一个形状；用 Markdown 写的程序则可以各自适配，不用碰底下的机器。skill 按代码对待：新 skill 通过 pull request 进来，合并前要评审，`CODEOWNERS` 把评审路由给维护者。

## 护栏大多不是自己造的

作者自动化了一套接触客户数据和 API 凭证的流程，放在全团队可见的仓库里，自己几乎没写代码。六个月前她会说这组合是鲁莽的，改变想法是因为意识到护栏早就在了。

自己造的部分是标准开发者习惯：`DRY_RUN` 开关、每个 pull request 上跑的测试套件、每次变更的代码评审。这些保护营销工作和保护软件一样有效。

真正起作用的是平台自带的：

- **Secret scanning 与 push protection。** 最可怕的场景是误提交 API token。push protection 在 secret 落进仓库之前就拦下推送；即使是 GitHub 自己的 token 漏了过去，也会被自动吊销。
- **Copilot 的数据策略。** 注册名单是业务数据，固定脚本用固定方式处理，但真实工作从不完全固定——总有某天需要一份没有脚本预料到的临时切片。因为企业版计划不保留 prompt、不用它训练模型，这类一次性分析可以直接问，而不必像行业里很多人悄悄做的那样，把业务数据粘进隔壁标签页的消费级聊天机器人。用哪些模型也由组织策略决定，不由个人判断，所以连一次性实验都在公司已经划定的边界内。安全路径和便捷路径这次是同一条。
- **按任务配模型。** 因为每个程序现在是命名、固定的工作单元，可以从组织批准的模型里挑：日常清洗名单用快而便宜的，起草 campaign 文案用更强的。

还有一个诚实的失败案例：早上的筛选工作流曾经静默失败五天，直到有人发现名单已经过期。**没有监控的自动化是带延迟的定时炸弹。** 每个定时工作流都要有大声抱怨的途径。

## 从一个任务开始

选你每周最重复的那件事，然后检查它经过的工具是否有 API 或 CLI——有的话比想象中多。

然后做最小版本：一张捕获输入的 Issue 表单、一个表示「开始」的标签、一个只做一步的 Action。或者跳过这些，直接把 runbook 写成 `SKILL.md` 让 Copilot 执行。带 dry-run 开关跑到你信任它为止，再往上长。

这套系统的可复制性不来自事件营销这个场景，而来自一个判断：把已经知道的做事方式写下来，平台会完成剩下的部分。你的「每天早上那份注册名单」大概也只是一份写下来的 runbook 之遥。
