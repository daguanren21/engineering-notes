> 同时运行五个 Agent，不等于拥有一支 Agent 团队。如果信息仍要由人复制、任务仍要由人分派、质量仍要由人逐项检查，系统的吞吐量依然受同一个人的注意力限制。

Codez 的文章以 Raft 为例，给出八步多 Agent 协作方法。它既是一篇 Agent Team 设计文章，也包含明显的产品说明和产品数据。阅读时需要把两者分开：身份、共享任务、交接和独立 Review 是可迁移的系统原则；具体规模、经济性和使用效果则是原文陈述，需要独立证据才能推广。

这篇笔记关注前一部分：到底增加哪些基础设施，多个 Agent 才从并行进程变成协作系统。

## 五个窗口为什么仍然只有一个人

最常见的“多 Agent”形态是多个聊天窗口：同一个人把 Agent A 的发现复制给 Agent B，再把 B 的结果交给 C，最后自己检查所有输出。

表面上有五个执行者，实际上只有一条共享总线——人的注意力。

```text
Agent A ─┐
Agent B ─┼→ 人工复制上下文 → 人工路由 → 人工审查
Agent C ─┤
Agent D ─┤
Agent E ─┘
```

增加窗口只增加并行生成能力，不会自动增加组织能力。只要其他 Agent 看不到已经发生的工作，人的输入仍然是系统瓶颈。

## 团队的最小定义是连续性

原文给出的判断很精确：真正的 Agent Team 不是“同时执行”，而是**前一个成员发现的事实，后一个成员能够继续使用。**

要形成这种连续性，系统至少需要：

- 稳定身份：谁负责什么领域；
- 共享历史：工作过程在哪里；
- 任务状态：谁拥有、进行到哪、是否待审查；
- 交接协议：完成后交给谁；
- 独立评价：谁有权拒绝；
- 权限边界：哪些事实与外部协作者共享。

并行是调度能力；连续性才是团队能力。

## 一、先建立共享工作空间

第一步不是创建更多 Agent，而是创建一份共同事实。

共享空间让人和 Agent 看到相同的频道、任务和历史。项目可以按频道划分，但不要为了每个项目重新建立互不连通的组织，否则独立性本身又变成需要人工搬运的边界。

这里可迁移的设计原则是：

> 团队需要一个权威协作空间；项目隔离应该发生在任务和权限层，而不是让每个执行者拥有自己的历史版本。

这个空间不一定长得像 Slack。它可以是 Issue Tracker、任务数据库、仓库状态树，或任何能保存所有权、状态和讨论记录的系统。

## 二、把执行留在自己的机器

原文中的 Raft 让 Agent 通过本地进程运行在用户自己的机器上，并连接不同 Runtime，例如 Claude Code、Codex CLI、Gemini CLI 或 OpenCode。

系统设计上的价值是把两个层分开：

```text
协作控制面    身份、任务、频道、交接
本地执行面    文件、工具、模型订阅、运行环境
```

Agent 可以更换推理 Runtime，而身份、工作区和记忆保持不变。这样模型不再等于 Agent，Runtime 只是可替换的推理引擎。

本地执行并不天然安全。安装脚本、网络权限、凭据和工作区访问仍需审核。不要因为进程运行在自己的机器上，就跳过最小权限和隔离边界。

## 三、按角色雇用 Agent

一次 Prompt 会在窗口关闭后消失；角色则应该拥有持续身份、领域、记忆、工作区和停止边界。

好的角色定义回答四件事：

1. 你唯一拥有哪个领域；
2. 什么样的结果算好；
3. 工作前应该读取什么；
4. 你不能做什么，以及完成后交给谁。

例如 Researcher 不应该只写“负责研究”，而要明确：每个结论必须带来源；无法验证时标记不确定；只研究和起草，不发布、不联系外部人员；输入准备完成后交给 Writer。

角色按领域分工，而不是按临时动作分工。新任务出现时，如果团队无法立即判断由谁承担，边界仍然模糊。

## 四、用任务而不是消息交付工作

消息只有内容；任务还拥有 Owner、State 和保存整个尝试过程的 Thread。

典型流程是：

```text
待领取 → 进行中 → 待审查 → 通过 / 退回
```

适合某个角色的 Agent 可以主动领取任务。完成后进入 Review，不等于获得发布权限。

任务结构最重要的长期收益不是单次更快，而是六个月后，决定和证据仍附着在原工作上。后来加入的人或 Agent 可以通过线程恢复背景，而不是再次向任务发起者询问。

## 五、让 Agent 直接交接

如果每个 Agent 完成后都把结果交还给人，人仍然是路由器。

角色说明中必须命名下一位 Owner：Researcher 完成后在同一 Thread 交给 Writer；Writer 缺来源时直接询问 Researcher，而不是把问题抛回用户。

交接协议需要保存：

- 当前任务和验收标准；
- 已产生的事实、产物和证据；
- 未解决问题与风险；
- 下一位 Owner 和触发条件。

原文还把定时提醒视作时间方向上的交接：Agent 可以按计划重新执行检查，把结果主动发布到频道。这样工作既可以在成员之间横向移动，也可以跨时间继续，而不必每次由人启动。

## 六、把审查放进团队

单个助手存在结构性问题：用户天然成为它的质量控制。Agent 越多，用户需要检查的输出越多。

解决方式不是让作者“再自我检查一次”，而是引入独立 Reviewer：

- Reviewer 不能是原作者；
- Reviewer 只检查，不顺手重写；
- Rubric 写明确拒绝条件；
- 退回时指出具体位置与原因；
- 用户看到通过结果，也能看到发生过哪些退回。

“检查质量”会得到泛泛批准；“无来源事实、越界内容和未验证数字必须退回”才会得到可执行审查。

独立不只指不同 Prompt。真正独立还包括不同上下文、不同角色激励，以及不依赖作者自己提供的结论。

## 七、共享房间，而不是整个服务器

跨组织协作通常在两个坏选项之间选择：共享整个工作区，或者由两边的人不断转述。

原文介绍的 Joint Channel 是第三种边界：两个独立服务器只在一个私有房间连接，各自决定哪些人和 Agent 进入。其他频道、历史、成员与权限保持本地。

这背后的通用原则是：

```text
共享最小协作面
≠ 共享整个组织状态
```

跨边界流动的应该只有参与者主动发布到该房间的消息、附件和 Agent 输出。对方不能浏览本地团队的其他历史，也不能替本方添加成员。

边界本身就是产品能力，而不是部署后的附加策略。

## 八、让一个 Agent 代表整个后台团队

最后一步让房间里的 Agent 不只回答自己知道的内容。它可以把问题带回本地团队，在拥有完整私有上下文的后台完成研究、查询或审查，再把必要答案带回共享房间。

```text
外部问题
  ↓
联合频道中的代表 Agent
  ↓
本地私有团队协作
  ↓
经过筛选的答案返回联合频道
```

这和普通 Bot 的区别在于，外部人员面对的是一个入口，但入口背后有任务、角色、工具和 Review Loop。与此同时，外部协作者只看到最终被带回房间的内容。

这里的风险同样明显：代表 Agent 必须知道哪些信息允许离开本地边界。没有数据分类、来源标记和发布策略，“回到后台再回来”可能成为泄露通道。

## 哪些原则可以脱离 Raft 复用

不使用 Raft，也可以复用以下原则：

| 原则 | 最小实现 |
| --- | --- |
| 共享事实 | 一个任务板和线程化历史 |
| 持久身份 | 明确领域、记忆和状态 |
| 任务所有权 | Owner、状态、验收条件 |
| 直接交接 | 下一 Owner 与交接产物 |
| 独立审查 | 作者之外的 Reviewer 与拒绝 Rubric |
| 控制面与执行面分离 | 协作状态不绑定具体模型 Runtime |
| 最小跨组织边界 | 只共享被明确发布的内容 |

这些能力可以由 GitHub Issues、Linear、Slack、数据库或自定义 Harness 组合实现。真正重要的是权威状态和转换规则，而不是界面的外形。

## 哪些内容需要保留怀疑

原文声称 Raft Beta 覆盖两万多名 Builder，也描述其自身团队超过一百个命名 Agent，并称绝大部分公司运营发生在产品内。这些都是来源文章中的产品陈述，本文没有独立验证。

类似地，“本地运行所以没有额外 Token 账单”只在用户现有订阅、Runtime 条款和具体使用方式允许时成立。成本、数据边界和服务可用性都需要结合真实配置判断。

区分证据层级很重要：

- 产品存在某项机制，可以通过文档和运行验证；
- 某团队使用该机制，可以通过可审计记录验证；
- 该机制普遍提升效率，需要对照实验才能验证。

不要把三者混成一个营销结论。

## 从四步内部闭环开始

原文最后建议先完成内部四步，再打开跨组织房间。一个更保守的落地顺序是：

1. 建立共享任务与历史；
2. 给 Agent 划分稳定角色；
3. 让任务在 Agent 之间直接交接；
4. 增加独立 Review 和明确拒绝条件；
5. 证明内部闭环稳定后，再引入定时自治；
6. 最后设计跨组织共享和数据发布边界。

如果内部交接仍需要人复制上下文，增加联合频道只会扩大协调面。先证明“前一个 Agent 的工作能被下一个 Agent 直接继承”，再谈 Agent Team。
