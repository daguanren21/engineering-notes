## 补丁版本暴露的是状态机的裂缝

v0.22.3 是一个补丁版本，没有新 API，没有新抽象。它修的全是同一类东西：**在某个边界上，系统对"当前处于什么状态"的判断和真实情况不一致**。审批、恢复、会话启动、追踪缓存、子进程生命周期，五处不同的代码，同一个病因。

这类缺陷在功能测试里几乎不会暴露，因为它们只在并发、中断、跨平台、或凭据缺失时才显形。读这份 changelog 的价值不在于记住修了什么，而在于认出这些边界，然后检查自己的 Harness 有没有同样的缝。

```flow
title: 一次工具调用要穿过的状态边界
caption: 每一层都可能对状态做出错误假设，补丁集中在这些接缝上
layer: 模型输出 | 工具调用意图 | *参数校验*
layer: 审批层 | 条件审批 | 人工确认 | 权限判定
layer: 执行层 | 工具查找 | 子进程 | 沙箱路径
layer: 持久层 | 会话存储 | 追踪缓存 | 恢复点
```

## 审批必须绑定已校验的参数

第一个修复是 `align conditional approvals with validated tool arguments`。条件审批的逻辑是：根据工具调用的参数决定要不要人工确认。问题在于，审批判定所依据的参数，和执行时真正使用的参数，可能不是同一份。

如果审批看的是模型原始输出，而执行用的是经过 schema 校验、补默认值、做类型转换之后的参数，那么两者之间就存在一个可被利用的间隙。攻击面很直白：构造一份能通过宽松审批的参数，再让它在校验后变成另一种语义。

正确的顺序是固定的——先校验，再审批，最后执行，且审批和执行共享同一个参数对象。任何在审批之后重新解析参数的实现，都等于把审批变成了装饰。

## 恢复路径上的失败也要有输出

第二个修复是 `deliver tool-not-found output on server-managed resume`。当服务端管理的会话从某个恢复点继续时，如果模型请求了一个不存在的工具，这条错误信息没有被送回模型。

这看起来只是少了一条消息，实际后果更严重。Agent 的执行循环依赖工具结果来推进：成功有结果，失败也必须有结果。如果失败被静默吞掉，模型会停在等待状态，或者更糟——基于缺失的信息继续推理，编造一个它以为发生过的事实。

恢复路径是最容易漏掉错误分支的地方，因为正常路径已经跑通了，恢复路径只在中断后触发。判断标准很简单：**任何一条进入执行循环的路径，都必须能产生工具结果，包括失败结果。**

## 会话与追踪层的缓存假设

会话层有两个修复。`handle concurrent async SQLite startup` 处理的是多个协程同时初始化同一个 SQLite 会话存储时的竞争——初始化不是幂等的，并发进入会互相破坏。`do not forward session limit as Conversations page size` 则是把两个语义不同的参数混用了：会话的历史条数上限，和分页请求的页大小，不是一回事，前者是业务约束，后者是传输细节。

追踪层修的是 `do not cache a missing OPENAI_API_KEY`。凭据缺失被当成一个可缓存的结果，于是进程启动时没有 key，之后即使补上也不会生效。缓存"不存在"是一种危险优化：它把一次瞬时状态固化成永久结论。凡是缓存否定结果的地方，都要问一句，这个否定会不会变。

```flow
title: 并发启动会话时的竞争
caption: 初始化不是幂等的，两个协程同时进入就会互相覆盖
layer: 协程 A | 检查存储是否存在 | *创建表结构*
layer: 协程 B | 检查存储是否存在 | *创建表结构*
layer: 结果 | 重复建表或半初始化状态 | 后续读写失败
```

## 子进程与路径的平台边界

扩展层修了三处。`reap subprocesses on early stream close` 处理流被提前关闭时子进程没有被回收——流关闭不等于进程结束，父进程必须显式清理，否则会积累僵尸进程。`preserve exact IDs in delete_branch` 说明分支删除时 ID 被做了某种规范化，导致删错了对象；标识符在任何环节都不该被"整理"。

沙箱层的 `keep command paths POSIX on a Windows host` 是跨平台经典问题：在 Windows 上运行，但沙箱内部约定的是 POSIX 路径语义。宿主平台和沙箱语义必须解耦，否则同一份配置在两种环境下行为不同。

## 这份 changelog 给出的检查清单

把六类修复抽象出来，就是一份可以直接对照自建 Harness 的清单：

| 边界 | 要问的问题 |
| --- | --- |
| 审批 | 审批依据的参数和执行使用的参数是同一个对象吗 |
| 恢复 | 恢复路径上的失败会作为工具结果返回吗 |
| 初始化 | 会话存储的初始化是幂等的吗 |
| 参数语义 | 业务上限和传输分页参数是否被混用 |
| 缓存 | 有没有缓存"不存在"这类会变化的状态 |
| 资源 | 流关闭、异常退出时子进程会被回收吗 |

这份发布里没有架构变化，全是接缝处的对齐。对使用这个 SDK 的人来说，升级即可；对自建 Agent Runtime 的人来说，这六条是低成本高回报的自查项——它们对应的缺陷都不会在 happy path 上出现，但都会在生产环境里以难以复现的形式出现。
