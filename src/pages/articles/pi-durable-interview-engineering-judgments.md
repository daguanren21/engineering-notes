## 人负责架构边界而不是逐行代写

**AI 编码的瓶颈不只是能否生成代码，而是设计判断、正确性反馈，以及无人看管时的运行可靠性。** 以下按议题整理完整访谈的观点；产品体验属于对话参与者的观察，不当作独立基准测试。

维护成本是第一个约束。Pi 加入 Earendil 的一个目标，是增加能够持续维护项目的人，降低对 Mario 一个人的依赖。Agent 能修不少小问题，但维护者仍要判断哪些 issue 值得处理，哪些触及设计、需要重新划分边界。生成补丁的吞吐量，不等于维护者判断力的吞吐量。

Armin 指出，Agent 几乎总通过增加代码修 bug。局部条件和补丁越积越多，完全自动化的代码库容易随着每次修复持续膨胀。他也承认自己使用 Agent 时同样会产生大型改动；这不是把问题归咎于其他使用者。

Mario 给出了正面的分工示例：先设计 Pi TUI 的底层和 API，再让 Agent 实现 Markdown、文本等组件。只要符合接口、渲染测试成立，他不要求逐行读代码。性能出问题时，Agent 擅长找局部热点，却未必能发现导致一系列热点的架构问题。

下面把这套分工放在一条反馈链中：实现可以委托，边界和验收不能消失。

```flow
title: 委托实现不能撤掉工程判断
caption: 人定义边界，Agent 实现，验证结果决定继续还是退回设计
layer: 设计 | 问题取舍 | *接口与架构边界*
layer: 实现 | Agent 编写组件 | 局部修复与实验
layer: 验证 | 测试与运行证据 | 性能和复杂度反馈
layer: 裁决 | 接受实现 | 返回设计层修正
```

对“模型架构能力是不是退步了”，Armin 的回答带有限定：模型可能更强，但使用者交出了更多控制权、提高了预期，最终结果反而更复杂。不能把这种体验直接写成模型能力下降的测量结论。对模型表达越来越晦涩的抱怨，也是在谈产品沟通成本，不是架构能力的证据。

## 可验证反馈决定自主执行的范围

他们对逆向工程、设备研究、模拟器、格式实现和模糊测试的进步非常肯定。关键不是这些任务“简单”，而是很多步骤有明确反馈：程序是否运行、行为是否与参考实现一致、测试是否通过、fuzzer 是否找到反例。

Mario 将这种正确性依据称为 **oracle**。有成熟测试集、规范和参考实现时，Agent 可以持续尝试、观察、修正；人仍可在关键处引导，但不必逐步指挥。Armin 的序列化库例子也是先实现格式，再持续 fuzz，找到错误后继续修复。LLM 还能补充常规生成器没有覆盖的案例。

这不等于“测试通过就证明整个软件正确”。反馈覆盖不到的设计约束、安全边界和真实使用路径，仍在验收范围之外。

架构短板可能与训练信号有关。模型能讨论合理架构，却不一定在自主实现时走向那个方案。最终代码和运行结果容易留下，设计如何形成、哪些选择被推翻、为何放弃一版方案，往往没有完整的文本记录。

Pi Durable 经历了约八轮迭代。即使保留所有对话，也不能直接把它们都视为同等质量的训练样本：需要知道哪轮方案最终采用、后续是否有效，以及哪些内容只是失败探索。访谈进一步讨论了轨迹分类、结合仓库历史和使用情况筛选信号的可能性。**这是对训练数据和反馈困难的解释与猜想，不是对实验室内部流程的核实，也不是“AI 永远不能做架构”的结论。**

## 可靠运行需要独立的持久执行层

Pi Durable 的目标是进程在模型调用或工具执行中死亡后，新进程可以从已保存的工作状态继续，而不是让用户查看聊天记录后再输入“继续”。

访谈把基础机制分成两块：

- **Durable task。** 执行前记录意图和输入，执行 effect，执行后保存结果；外部动作是否能安全重试，取决于幂等键、状态查询等配合，不能由 Harness 单方面保证。
- **带版本的应用文档。** 待办列表、画布等状态与对话位置关联。回到过去时，有的状态要取当时版本，有的要保留当前版本。它不只是保存模型看到的文本。

他们明确说方案不是依赖重放整个事件历史的 event sourcing。讨论 JSON Patch、不可变数据、CRDT 和 JavaScript Proxy 时，也承认现有工具不完全符合需求、自身实现有成本和限制；没有把某个状态管理技术包装成通用答案。

长历史也不能永远全部装进内存。一个存在多年的 Slack Agent 需要保存完整历史，但模型上下文和运行时工作集应该有边界。更细的恢复规则、关机与取消的区别，见文末[同主题过刊](#related-title)中的《Pi Durable：关机与主动关闭后的恢复边界》。

单独建设基础层，是因为其他产品虽然也解决了部分持久化问题，但这些能力通常与具体产品绑定，不容易拿来构建另一种 Agent。模型本身已经不确定，外围编排至少应该可靠、可理解。

Earendil 同时建设可复用基础设施和面向非工程师的产品，不希望长期只是一家 coding agent 公司。个人助手应帮助使用者解决问题，而不是把生成内容和沟通负担倾倒给外部的人。

下一步的方向是多个人、多个 Agent、多个设备之间自由组合协作。Mario 用 Pi Mobile 做自用验证：除模型推理外，其余逻辑在手机上运行，工具可以连接远程机器执行。这是验证 Pi Durable 的实验，当时并非承诺发布的正式产品。按[官方发布说明](https://earendil.com/posts/pi-durable/)，Pi Durable 也是独立的实验包，不是已经替换普通 Pi coding agent 的运行内核。

## 其他 Harness 是设计参照而非功能清单

对其他 Harness 的讨论是经验交流，不是同一任务、模型和成本约束下的横向测试。逐项记录时，应保留这种证据等级，不能把不同参与者的体验全部归给 Mario 或 Armin。

| 对象 | 对话中的判断 | 应保留的限定 |
| --- | --- | --- |
| Codex | 后端出问题时会读开源实现，了解客户端为兼容后端做了什么 | 属于针对问题的源码调查，不是全面评分 |
| OpenCode | 留意过 B2，以及持久化方向的工作 | 没有给出持续使用或完整评测结论 |
| Amp / Orbs | 欣赏团队的愿景、执行力和不夸大宣传；看好 Orbs 思路 | Mario 明确说没用过 Amp，主要看过演示、接触团队；Armin 用过，但对 Web 形态黏性不强 |
| Pi | 开源、可理解，适合作为构建自己工具的基础 | 偏好不等于所有场景下性能最好 |
| Omp | advisor 用强模型纠偏，子 Agent 扇出、连接服务等能力有用 | 同时讨论了 token 消耗和系统提示词过大的成本 |
| DeepSeek harness | 插件、自我修改思路和简洁体验值得借鉴；Web 进程便于跨设备访问 | 部分插件承诺尚未完全兑现；不等于 Pi 要复制其实现 |
| Claude Code | 比以前稳定，自我修改方向值得关注 | 对话仍提及随机错误和会话串线，未在本笔记独立复现 |
| Droid | 收尾时表达了使用偏好与对团队的认可 | 随后的批评是 AI 项目容易累积半成品功能，并非专门针对 Droid 的实测结论 |

Armin 不愿花太多时间追逐竞品，因为别人加一个功能，可能是在解决真问题，也可能只是代码便宜、顺手做了实验。桌面、终端、Web 和手机也没有现成赢家；他不特别喜欢终端，但仍没找到完全满意的桌面体验。

## 技术选择应随证据而不是立场变化

Armin 解释 Codemode 的直接需求来自 Jev：分类器需要外围代码和专门的 Harness 驱动，从这个能力继续接到 MCP 很自然。

有些任务需要模糊判断，但通用 LLM 的速度不适合批量处理。训练得当的通用 one-shot 分类器为邮件等场景提供了另一种选择。这里的判断不是“用小模型替代所有大模型”，而是按任务所需的能力、延迟与编排成本选择模型类别。

Pi 从不内置 MCP 转向支持，也是因为模型训练、服务质量和标准成熟度发生了变化，权衡结果随之变化。Mario 强调这不是追热点，而是长时间考虑后作出的决定。极简意味着拒绝没有足够价值的复杂性，不意味着永远拒绝某个功能。更具体的工具发现与执行边界，可对照过刊《MCP到Code Mode的工程演进》。

## 安全与上手体验决定实际价值

个人 Agent 接入越多账号和私密数据，误操作的后果越大。访谈中的文件系统暴露、财务信息误发属于对话里的案例与转述，不应当作本笔记核实过的事故报告。

多人共享、Agent 可扩展 UI 时，服务器端 Docker 沙箱不能自动解决浏览器端的 XSS、Cookie 外泄和参与者间的信任边界。iframe 可以参与隔离，但会带来体验和集成成本；IPFS 的存储、复制能力也不能直接解决信息外泄。**安全并非原则上无解，而是不能从产品复杂度里删掉。** 忽略安全可以做出顺滑演示，却可能摧毁信任。

Armin 对已有 AI 能力基本满意，更希望体验改善、炒作消退，社区用它构建有价值的软件，而不是不断制造低质量复制品。对科研突破、游戏保存等应用的期待，不应转写成访谈已经证明这些目标全部实现。

上手引导尤其不能省略。给普通用户一个聊天框和侧边栏，再要求他“用 AI 提高效率”，没有解释它能做什么、不知道时怎么提问、怎样完成一项具体任务。家庭研究、生日游戏等例子说明，他们重视技术如何进入实际生活，而不只是继续“用 AI 做 AI”。

生成代码便宜，不代表把大量只完成一部分的功能塞进产品是免费的。反复报错、Agent 不断提问却不执行，会消耗用户注意力。功能是否完整、控制是否符合用户意图，比功能清单更长更重要。
