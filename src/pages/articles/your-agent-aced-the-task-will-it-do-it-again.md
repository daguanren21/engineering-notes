## 平均值掩盖了不可复现的成功

一个 ReAct Agent 在 AppWorld 上跑五次，平均成功率 77.4%。这个数字看起来足够上线。但同一个任务五次全部成功的比例只有 53.0%。两者相差 24.4 个百分点，在困难任务上这个差距能到 30 点。

差距的来源不是模型能力不足，而是同一任务在没有任何外部变化的情况下，Agent 有时能做对、有时做不对。用户重复问同一个问题，得到的不是稳定的答案。对于对账、合同义务核查这类工作，这直接决定系统能不能用。

大多数 benchmark 只报平均值，也就是 Mean@k：跑 k 次取平均通过率。它回答的是「这个 Agent 平均有多好」，而不是「我再问一次它还会不会做对」。后者需要的是 Pass^k，即 k 次全部通过的任务占比。

```flow
title: 两个指标问的是不同问题
caption: 同一批 k 次运行，Mean@k 取平均，Pass^k 要求全中，二者之差就是一致性缺口
layer: 运行层 | 第 1 次 | 第 2 次 | ... | 第 k 次
layer: 统计层 | *Mean@k 取平均* | *Pass^k 要求全中*
layer: 判断层 | 平均能力 | *可复现性*
```

注意 Pass^k 与 Pass@k 不是一回事。Pass@k 问的是 k 次里至少成功一次，适合可以验证并重试的场景；Pass^k 是它的悲观镜像，要求每一次都成功。三者恒有 Pass^k ≤ Mean@k ≤ Pass@k。

## 决策分布的形状决定了会不会翻车

Agent 每一步决策——调哪个 API、传什么参数、要不要重试——都来自一个 next token 的概率分布。关键在分布的形状。

尖锐的分布把大部分概率质量压在单个 token 上，第二名远远落后，同样的选择会一次次复现。平坦的分布把相近的质量摊在几个近乎并列的 token 上，谁胜出接近抛硬币。

形状决定了需要多大的噪声才能改变结果。尖锐分布对 GPU 浮点非结合性、请求批处理这类平台侧扰动有免疫力；平坦分布则会被同样的微小扰动重新排序。而一条轨迹串联了几十个决策，每步很小的翻转概率会累积成整条轨迹走偏的显著概率。24 点的缺口就是这么来的。

这也解释了为什么调解码参数没用。贪心解码和固定随机种子管的是「如何把分布变成一个 token」，管不了分布本身。在托管端点上，概率本身每次运行都会有细微漂移，所以 temperature 设为 0、同一个 prompt 打给同一个模型，今天和明天仍可能把一次近乎并列的决策判向不同方向。实验中的 ReAct Agent 就跑在 temperature 0.0 上，上面的方差没有一分来自常规采样。

## 用一次重采样定位易翻转的决策点

问题于是变成一个搜索：给定一条轨迹，哪些步骤是平坦的？

Consistency Analyzer 的做法是受控重采样。对已记录轨迹中的每一个决策步骤，用当时已经记录下来的上下文，额外发一次模型调用，一次请求 k 个 completion（默认 k=5），测量该点的输出实际波动有多大。它不发起新的 tool call，不与环境交互，也不重新端到端跑一遍任务。每个决策步骤得到一个一致性分数，写进 scorecard，标出下一次运行可能翻转的位置。

整个过程是黑盒的：不需要 logits，不需要模型内部信息，除了已有的 trace 之外不需要任何埋点。这一点决定了它可以用在生产流量上——很多场景下你连完整重放一次任务都做不到。

```flow
title: 从一条轨迹到可复用的准则
caption: 检测阶段离线重采样定位易翻转步骤，生成阶段把每个被标记的步骤写成准则并注入推理上下文
layer: 输入 | 一条已记录轨迹
layer: 检测 | 逐步重采样 k=5 | *一致性分数* | scorecard
layer: 生成 | 候选准则 | 存入 ALTK-Evolve
layer: 推理 | 检索注入 | 稳定决策点
```

## 准则针对的是不稳定，不是失败

每个被标记的步骤都会变成一条候选一致性准则，沿用 ALTK-Evolve 的标准格式，因此可以直接进入既有的存储与检索管线。

一个真实例子来自 AppWorld 任务「How many activities are done in my bucket list as per my SimpleNote note?」，由 GPT-4.1 从轨迹中生成：

- 统计笔记内容里的 checkbox 标记时，用行锚定的正则匹配，而不是普通子串计数——笔记标题常在图例行里重复出现该符号。
- 对笔记查询的搜索结果，先检查是否存在多个匹配、确认选对了笔记再继续。

这两条都不是某个任务的冷知识。字符串计数 bug 和未经验证的搜索结果，是在大量 AppWorld 任务中都会出现的高不确定性决策点。关键在于分析器瞄准的是不稳定而非失败，所以它能抓到那些这次碰巧做对、下次很容易做错的步骤。

## 缺口减半，平均准确率不降

在 AppWorld test_normal 的 168 个任务上，用 GPT-4.1 的 ReAct Agent，每个任务从一条基线轨迹生成一致性准则，然后在 5 次全新运行上测试。

| 指标 | 基线 | 加准则后 |
| --- | --- | --- |
| Mean@5 | 77.4% | 81.0% |
| Pass^5 | 53.0% | 69.0% |
| 一致性缺口 | 24.4pp | 12.0pp |

按难度分层看，中等任务 +22.9pp（相对 +44%），困难任务 +14.3pp（相对 +45%），两者相对提升基本持平，中等任务绝对增量更大；简单任务 +12.2pp，本来可提升空间就最小。

Mean@5 在每一层都没有下降。保持平均准确率是硬性要求而非加分项：如果靠牺牲 Mean@5 来换 Pass^5，只是把不可靠性挪了个位置，并没有解决问题。

准则还能迁移。应用到同一 AppWorld 场景下另一个相关任务时，Pass^5 仍提升 +13.0pp，只比同任务数字低 3 点。在更弱的模型 gpt-oss-120b 上，同任务 Pass^5 从 10.1% 升到 16.1%（+6.0pp），而相似任务的泛化增益 +8.7pp 反而超过了同任务增益，说明准则抓到的是可复用的失败模式，而不是记住了某条轨迹的具体细节。

## 上线前先报 Pass^k

把 Pass^k 和 Mean@k 一起报出来。平均值区分不了可靠的 Agent 和运气好的 Agent，哪怕 k=3 也能暴露出你原本不知道的缺口。

预期缺口随难度扩大。最难的那一档，单一平均值最具误导性。

不要一上来就换更大的模型。一致性与能力是正交的两个轴，更强的模型抬高 Mean@k，未必缩小一致性缺口。

诊断不需要 grader，也不需要实时重放。每个决策步骤多一次 LLM 调用（默认采样 k=5 个 completion）就够了，不需要 ground truth，不需要把任务重新跑进环境。这正是它能用在生产流量上的原因。
