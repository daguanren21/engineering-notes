## 直接连接的问题不是效率，是可靠性上限

ZippyDB 是 Meta 使用最广的 key value store，支撑产品元数据、计数器和配置，全球分布式集群每秒可服务数十亿次操作。它的客户端超过一百万台主机，归属数百个团队，无法快速统一改动。

在直连模型里，每个客户端连到它需要的每一个数据库主机。一个客户端在一个稳定窗口内可能触及数万个不同 shard，而这些 shard 分布在数十万台数据库主机上。结果是密集的多对多 TLS 连接网格：典型客户端持有数万条出站连接，典型数据库主机接受数万条入站连接。

```flow
title: 直连网格与 Proxy 收敛
caption: 上半部分是客户端与数据库主机之间的多对多连接，下半部分把扇出与扇入各自收敛成有界的两跳

layer: 直连模型 | 客户端群（百万级） | *多对多 TLS 网格* | 数据库主机（数十万）
layer: ZGateway 模型 | 客户端 | *区域 Proxy 层* | ZServer 副本
```

网格的代价不只是浪费。每条连接在两端都占内存、CPU 和文件描述符，且大部分时间空闲；入站连接数随客户端规模增长，每新增一批客户端就让每台数据库主机更糟。更麻烦的是每个客户端自己管理连接池和 failover，一旦连接复用率骤降——某批客户端重启、一次 deploy 滚动——就会形成新连接风暴。Meta 追踪到过主机因文件描述符耗尽和 OOM 崩溃，原因正是这个。

客户端侧很难修，因为两套系统同时在动：客户端集群不断调整池化策略并扩张，数据库集群按自己的节奏合并。把两者直接耦合，像是在两辆行驶中的车之间跳来跳去。

## Proxy 把无界扇入换成自己控制的常数

ZGateway 是位于 ZippyDB 客户端与 ZServer 集群之间的无状态 Proxy 层，可处理超过每秒 10 亿次操作，承载约 40% 的 ZippyDB 流量，预计增长到 60% 以上，对平均用例只增加约 6% 的计算开销。它以区域 tier 形式运行，通过 ServiceRouter 发现，保证每个客户端靠近自己的 gateway，有两种形态共享同一条 pipeline：纯 Proxy 和 read-through cache。它的引擎就是 Meta 自己的厚 C++ 客户端，每个用例一个内部客户端——ZGateway 本质上是把 ZippyDB 客户端当作托管服务来跑。

请求路径是：客户端通过 sticky 连接发到区域 ZGateway 主机，主机终止 TLS、按用例 ACL 鉴权，施加按租户的准入控制、校验和整形；解析 shard，在缓存 tier 上查本地缓存；未命中与写请求和同一 shard 的其他在途请求一起批处理、合并，再发往正确的副本；响应解复用回各调用方，沿途记录按用例的 metrics、trace 和配额使用。

关键性质是连接数的不对称：每个客户端只需要到区域 ZGateway 主机的 sticky 连接池，每台 ZServer 只看到来自 ZGateway 集群的连接，而后者规模由自己控制。有些职责被刻意留在原处——TLS 在 Thrift/ServiceRouter 栈里，key 到 shard 的映射在 shard locator 里，副本选择与 hedging 在嵌入式客户端里。ZGateway 负责流量管理，而不是重新实现数据库客户端。

用球入箱模型算一下：把 B 个球（一台主机触及的 shard）扔进 H 个箱（主机），数被命中的不同箱数。扇出是命中的不同箱数，扇入是这个概率乘以调用方规模。用一组取整的模拟数字——20 个区域、50 万台数据库主机、3 万台 Proxy 主机、100 万客户端、每客户端 5 万个 shard——每主机连接数下降约 97–98%（模型估算，逐对 TLS 倍数在比值中抵消）。连接没有消失，只是移到了为承载它们而建的 tier。端到端看，持久连接总数仍下降约 19 倍，因为每条后端连接复用了许多客户端。

但一次性的下降不是重点，重点是伸缩行为变了。直连模型下数据库主机的扇入是 H_client · p，对客户端规模线性，每批新客户端都让每台数据库主机更糟。有了 ZGateway，客户端规模从公式里消失：扇入约等于 R · S_host，即区域数乘以每主机 shard 密度，与两个集群的规模都无关。唯一剩下的杠杆是 shard 密度，而这个由自己掌握。一个由别人驱动的无界数字，变成了自己控制的有界数字。

## 批处理与合并：共享位置才能跨调用方做事

因为 ZGateway 处在许多客户端的路径上，它能做任何客户端库做不到的事——把互不相关的调用方的工作合并起来。每台主机上的共享 batcher 按用例和物理 shard 分组，把发往同一目的地的请求合并成一个后端 RPC。它还会 coalesce：多个调用方在同一时刻要同一个 key，gateway 只取一次，把结果扇出。客户端侧的 batcher 只能合并自己进程内的请求，gateway 能跨客户端合并。

每个 RPC 无论大小都带固定开销——Thrift 序列化、shard 查找、鉴权、系统调用——把许多操作折进一个请求就摊薄了全部开销：更少更大的后端请求、更低的 QPS 和 CPU、以及 linger 窗口抹平微突发后更平稳的负载。而且用例按发出的 QPS 计费，批处理等于拉长了它的限流预算，在客户端零改动的情况下减少被限流。

批处理还有两个好处与效率无关。第一是热 key 下的 coalesce：数千个同时到达的调用方塌缩成一次后端读，热 key 永远不会变成打向单个副本的踩踏。第二是它能让我们删掉什么：多年来想要批处理的客户自己跑客户端库，这些库脆弱、吃 CPU、各自调参，并且是持续的事故来源，因为复杂度散落在我们无法控制的一百万个二进制里。共享 batcher 能跨客户端批处理，这是那些库做不到的，于是它们被退役了。

每个请求停在一个内存 batch 里，在 linger 窗口到期、payload 超过大小上限、或请求数达到上限时 flush，因此增加的延迟有界；超大或刚迁移的 batch 回退为单独发送。把请求留在内存里有 OOM 风险，所以批处理带两个安全机制：idle eviction 处理缓慢增长，超过 TTL 的 batch-map 条目在下次 flush 时清除；in-flight cap 处理急性过载，当后端变慢时，运行已 flush batch 的协程堆积速度快于排空速度，计数越过上限后拒绝新的执行。日常卫生加急性安全阀，才让批处理默认安全。

## 共享层是限流、缓存和负载均衡的天然位置

流量一旦经过一个 tier，它就成了那些否则每个客户端都要重新实现的能力的天然归宿。

**租户隔离与准入控制。** 共享 tier 服务数百个用例，一个行为异常的租户不能饿死其他租户。ZGateway 的防御是 Discriminant Load Shedding（DLS）：每个请求映射到一个按租户的 bucket，以用例为键、按优先级拆分，bucket 之间 round-robin 排空。某个租户淹没 tier 时，它自己的 bucket 先满、多余部分被 shed，其他 bucket 继续排空——隔离是结构的性质，不是运气。DLS 之前，一个 CPU 并发控制器用 AIMD 循环调整共享 token bucket 的准入速度；内存处理器用同样方式防 OOM。

shedding 保持 discriminant。在一次约 1350 个活跃租户 bucket、CPU 超过 90% 的受控过载中，只有 6 个——真正的 noisy neighbor——在 shedding；其余约 1344 个执行了 99.9% 的请求且零拒绝，goodput 保持在 97–98%，这套机制本身消耗约 8% 的 CPU。

**带实时失效的读缓存。** 在缓存 tier 上，热读由进程内缓存服务；未命中时 gateway 取一把按 key 的 fill lock，于是同一个 key 的惊群塌缩成一次后端取数。新鲜度来自一条 change-data-capture 流，写事件和 checkpoint 事件会失效或重填受影响的条目，并遵守显式的有界陈旧契约；每台主机通过一致性哈希拥有一片 keyspace。回报是存储层可观的读卸载，延迟更低，且不牺牲正确性。

**跨 tier 负载均衡。** ZGateway 无状态，任何请求都能由区域 tier 内任意主机服务，所以可以把流量导向以均衡负载。但 tier 并不均匀：它混合了约 26 核到约 126 核的主机，一次大的任务替换能在几分钟内重排容量。对不相等的主机一视同仁会产生热点离群值，而一台过热的 ZGateway 主机会变成错误率尖峰和 ServiceRouter 限流。由于 ServiceRouter 按加权一致性哈希路由，杠杆就是每台主机的权重。

控制面 balancer 负责算权重：按固定节奏读取每台主机近期的 CPU 利用率，把 tier 平均值归一化为 1.0，然后让每个权重朝负载的反方向微调。护栏保证稳定——调整被阻尼和钳制，分布重新居中到目标中位数以免权重漂向零，变更节流每次只移动最不均衡的主机，限制 shard 重排（在缓存 tier 上代价高，因为移动权重意味着移动 key）。新主机按硬件容量缩放初始权重。教训是：一条固定策略无法同时服务平静的 tier 和受冲击的 tier，所以 balancer 正在变得自适应，先分类 tier 状态——稳定漂移、任务churn、初始权重平坦、双峰负载、热点离群、区域偏斜——再套用匹配的策略。

## 跨区容灾与事务：把正确性关键路径收成一条

ZGateway 在大部分生命周期里严格区域化，failover 不出一区。这对延迟很好，但当整个区域的 tier 承压时，请求在本地排队超时，隔壁的健康容量却闲置。因为 ZGateway 站在 ServiceRouter 上，可以受控地让路由跨越区域边界，有三种机制：global routing 构建跨区域路由表，让饱和的本地 tier 切到健康的 tier 而不是死在家里；mega-regions 把地理上接近的区域归为一个 locality，溢出就近泄流并保留大部分延迟收益；rings 明确声明哪些区域互为备份、按什么比例。三者都按 tier 和区域在百分比开关后面启用。

failover 信号和路由本身一样重要。简单的区域 CPU 平均值会抹平我们恰恰要抓的热点状况，所以 failover 依据一个更锐利的度量，调到在区域滑向过载之前触发，而不是之后。

事务需要一个地方保存客户端侧的记账：read set、扫描过的范围、pending writes。历史上这活在厚客户端里。当 ZGateway 把客户迁到 thin client 时，它必须迁到 gateway 上。第一版留下了两套并行实现——一套为 ZGateway 定制的存储，和引擎已经在用的内存路径——这是整个流程中最关乎正确性的部分出现了两个版本。后来合并成一套，藏在 flag 后面，分九个阶段推进到流量最高的区域，覆盖 100% 的事务流量且无可靠性回退。与引擎共享这条路径让 ZGateway 与服务端事务演进保持同步：在 tier 内演进一次能力，所有客户端自动继承。

## 共享层真正的产出是控制面

ZGateway 以大量服务器运行在数十个区域，按负载分成少数几个 tier：一个大型通用 tier 服务长尾用例，为最大客户设专用 tier，另有一个独立的高吞吐 Proxy tier。它们的足迹和规模相差一个数量级以上，单个 tier 内部也不均匀，主要因为 stacking——多个任务以不同密度打包在一台机器上，紧挨着全尺寸的专用主机。在所有这一切之上，ZGateway 暴露丰富的按用例可观测性，正是这种可见性让共享基础设施上的准入控制和负载均衡变得安全。

近期路线没变：把所有 ZippyDB 流量统一到 ZGateway。更有意思的问题是，一个被普遍采用的 gateway 让什么成为可能。三个方向共享同一个主题——ZGateway 既看得最多，也决定得最多。

**Agent 运营的启发式。** 这里几乎每个能力都由控制循环和手工调参的旋钮支配：限流 bucket 大小和 CPU 阈值、balancer 参数、failover 触发条件、batch flush 窗口、缓存陈旧上界。今天这些由人调、由 cron 推；上面那个自适应 balancer 已经是一个不叫 Agent 的 Agent。下一步是把它显式化，把这些启发式和内部状态暴露为结构化控制面，让 AI Agent 看我们看的同一份遥测——诊断 tier 状态、把事故归因到某个 noisy tenant、在护栏后施加修复，比任何 oncall 都快。

**Co-location。** ZGateway 是一个独立 tier，代价是多一跳网络和几个百分点的开销。对延迟或效率敏感的负载，可以把 gateway 的一部分下推到 ZServer 主机旁边，让 gateway-server 这一段变成本地调用，而控制面保持集中。难点是在不重新耦合我们刻意解耦的两个集群的前提下做到这一点：连接管理和准入控制的前端仍是共享的区域 tier，只有能从数据本地性获益的部分下移。

**多进程 gateway。** ZGateway 在一个进程里跑许多不同职责，所以一个租户的内存爆炸能威胁主机上的一切。拆成协作的进程——连接/TLS 前端、请求 worker、独立的缓存和事务组件——换来硬故障隔离和独立生命周期。这与 Agent 运营的启发式和 co-location 互补：Agent 可以管理主机上的进程集群，而当数据面本身就是一个可放置的进程时，co-location 也更干净。

这三件事合起来，把 ZGateway 从一个聪明的 tier 变成一个可编程的 tier：控制决策由 Agent 做，足迹移动到工作所在之处，故障域由构造隔离。判断是清楚的——当客户端规模大到不属于你、且无法快速改动时，把共享逻辑放进一个你控制的 Proxy 层，收益不在那一次连接数下降，而在扇入公式里客户端规模这一项被彻底消掉。
